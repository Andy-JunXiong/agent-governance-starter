01 · The first stopped run

The first replay never reached the build.

I allowed one no-retry replay to test the real cleanup path. The dry worker stopped first: its environment intentionally had no PATH, but the manifest check still tried to launch bare git.

That failure mattered because it showed the restriction was real. The easy fix would have been to put Git back into the worker environment. That would make the symptom disappear by weakening the boundary I was trying to test.

The decision: I did not retry the exhausted task, and I did not treat a wider environment as the default repair.

02 · The decision

I chose to move trusted facts, not widen the worker.

In plain language: Git could stay outside. The restricted path only needed the exact list of files and the identities that the controller had already checked. Internally, that became a split between a Git-backed entry check and filesystem-only revalidation.

03 · The second hidden dependency

The first repair was necessary, but inspection showed it was not sufficient.

After moving admission to the controller, read-only inspection followed the actual path. The caller reached the driver—but the driver still imported the same Git-backed checker. The coupling had moved out of the dry worker and remained one layer deeper.

The Agent proposed most of the low-level repairs. I evaluated and approved them against the boundary I wanted to preserve: the worker would remain PATH-free, and cleanup would still wait for verified evidence.

01

I moved Git admission outside the worker

Failure: the worker intentionally had no PATH, but its manifest check launched git.

Repair: move the sole Git-backed admission to the controller and pass only normalized manifest facts inward.

02

I removed the same dependency from the driver

Failure: inspection found the driver still imported the Git-backed checker before the build.

Repair: re-derive regular files and both identities from the filesystem before root allocation.

Key design choice: preserve the restricted environment instead of widening it. Drift now returns manifest_preflight_failed with zero action attempts, no root, no evidence, and no cleanup claim.

05 · The question answered

Yes—on this run, cleanup waited for evidence.

This was the behavior I set out to verify. The build succeeding was not enough; the evidence had to be written exclusively and its receipt had to match before removal became valid.

Before cleanup

Exclusive evidence write succeeds and the receipt is revalidated against the exact durable bytes.

→
Cleanup allowed

Remove only the exact short root, then observe a final short-root count of zero.

If evidence fails: retain the private recovery root. Do not manually clean it or claim success under the exhausted task.

This answers one local Windows replay. Cross-platform behavior and repeated reliability would need separate runs.

Interview follow-ups

Likely questions

Why not restore PATH or give the worker Git?

That widens the execution boundary to solve a data-flow problem. The controller already owns Git observation, while the driver proves point-in-time filesystem equality.

Why observe the manifest more than once?

The observations answer different questions: Git-backed admission before execution and filesystem equality immediately before resource allocation.

Why preserve a failed temporary root?

Deleting before durable evidence would destroy diagnostic state and create an unsupported cleanup claim. Recovery needs separate approval.

What would you build next?

Not yet decided. Candidates for product review are a clearer post-cleanup evidence template or a separate portability and repetition study.
