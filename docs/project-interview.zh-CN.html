AgentGov 项目故事

我做了 AgentGov，也逐渐发现它的重心正在偏移。

功能没有坏，测试也一直是绿的。但我越来越容易解释 GitHub 相关功能怎么工作，却越来越难解释它们给最初的问题增加了什么价值。

01

我为什么做它

Coding Agent 可以写出测试通过的代码，同时又做了人根本没要求的事。测试通过也不会告诉你，是不是已经有人同意让这个改动继续往前走。

我先做软件能够稳定检查的部分。AgentGov 会读人写下的任务、这个任务允许修改的文件，以及工作过程产生的证据。它可以说某件事通过了、失败了，或者仍然需要人来判断。我没有让它把这些检查自动变成“这个改动是正确的”。

02

我是怎么发现它开始偏移的

一次 consumer 实验暴露了真实摩擦：安装、Windows 路径、onboarding，还有命令理解。我开始改这些问题，然后是 CI，再然后是 PR 流程。这些功能都不是坏功能，它们确实有用，测试也一直是绿的。

我越来越容易解释这些 GitHub 功能怎么工作，却越来越难解释下一个功能到底给原来的业务问题增加了什么价值。

警告来自我本来就有的一个习惯。每做完一个功能，我都会写它的短期价值、长期价值，以及它和下一阶段的关系。连续几个功能之后，GitHub 和交付语言越来越主导路线图，而它们与原始业务需求的关系越来越难解释。

我没有把这种感觉当成证明。我回去把累积实现和最初需求放在一起检查。每个功能单独看都没错，但产品方向确实偏了。

功能都能工作问题不在局部质量。
路线图变了交付机制逐渐变成主线。
原始价值变模糊每个新功能越来越难连回业务问题。
03

我改了什么

我没有把 PR 或 CI 工作丢掉，而是把它们移出了中心。我先回到原始开发循环的最小版本，然后再补充周围细节。

主产品重新变得容易说清：人描述任务，约定可以改哪些文件，Agent 完成工作，软件检查当前文件和测试，最后人决定下一步。PR 和 CI 在之后重新检查同一组事实，作为后盾。

人描述任务约定可改文件Agent 完成改动检查实际文件运行当前测试人复核人决定PR 与 CI 稍后再检查
04

一个例子就能把产品说具体

在退款 Demo 里，Agent 正确修好了计算，同时又改了一条没有人要求的审批规则。测试仍然可以是绿的。AgentGov 把实际改动文件和任务对照，阻止完成，并把真正的选择留给人。

验证可以证明一个改动能工作，却不能告诉我是不是还在做正确的产品。

AgentGov 里没有什么东西能自动回答这个产品问题。我必须自己回到最初的问题，检查最近几个功能是不是仍然在加强它。

我现在把这当成一个开发习惯，而不是另一个等待自动化的功能。
