The AgentGov project story

I built AgentGov—and noticed its center of gravity drifting.

Every feature still worked. The tests stayed green. But I was getting better at explaining GitHub mechanics and worse at explaining what new value I was adding to the original product problem.

01

Why I built it

A coding agent can write code that passes its tests and still do more than the person actually asked for. Green tests also do not tell you whether anyone has approved the change to move forward.

I started with the part software could check reliably. AgentGov reads the task a person wrote, the files allowed for that task, and the evidence produced during the work. It can say something passed, failed, or still needs a person. I deliberately did not let those checks turn into “this change is correct.”

02

How I noticed it was drifting

A consumer exercise exposed real friction around installation, Windows paths, onboarding, and understanding the commands. I started improving those things. Then CI. Then PR workflows. None of those changes were bad. They were useful, and the tests stayed green.

I was getting better at explaining how the GitHub features worked—and finding it harder to explain what the next feature added to the original business problem.

The warning came from a habit I already had. After every feature, I wrote down its short-term benefit, long-term benefit, and how it connected to the next stage. After several features, GitHub and delivery language were taking over the roadmap, while the connection to the original business requirement was becoming harder to explain.

I did not treat that feeling as proof. I went back and compared the accumulated work with the original requirement. The individual features were fine. The product direction had drifted.

The features workedLocal quality was not the problem.
The roadmap changedDelivery mechanics were becoming the main story.
The original value blurredEach new connection to the business problem was harder to explain.
03

What I changed

I did not throw away the PR or CI work. I moved it out of the center. I returned to the smallest version of the original development loop first, then added detail around it.

The main product became easy to say again: a person describes the task, agrees which files may change, the agent does the work, software checks the current files and tests, and a person decides what happens next. PR and CI can replay the same facts afterwards as a backstop.

04

One example makes the product concrete

In the refund demo, the agent fixes the calculation correctly but also changes an approval rule nobody asked it to touch. The tests can still be green. AgentGov compares the changed files with the task, blocks completion, and leaves the real choice to a person.

Verification can prove a change works. It cannot tell me whether I am still building the right product.

Nothing inside AgentGov solves that product question automatically. I have to go back to the original problem and check whether the last several features are still strengthening it.

I now treat that as a development habit, not another feature to automate.
