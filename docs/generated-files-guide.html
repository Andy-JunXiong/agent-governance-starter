From scaffold to truthful governance

What each generated file means—and what to write in it.

Generated files are prompts for accountable project facts. Their existence is not evidence that governance is complete.

Start with facts, not ideal answers

If an owner, test set, or approval boundary is unknown, record that gap honestly. Do not replace a placeholder with a guess just to make a warning disappear.

AGENTS.md — operating rules

Describe scope, instruction precedence, validation commands, prohibited actions, escalation conditions, and actions reserved for people.

Example

Allowed: edit application and test files.
Required: run unit tests for changed modules.
Escalate: payment, access-control, or deployment changes.
Human-only: merge, release, production deployment.

Avoid vague statements such as “be careful.” Reviewers need observable boundaries.

docs/adr/ and INVARIANTS.md

ADRs record durable decisions, rationale, alternatives, owners, and follow-up. Invariants state properties that must remain true.

Example invariant

Property: Refund amounts above $100 require human approval.
Authority: Customer Operations Lead.
Verification: capability manifest + refund integration test.
Escalation: stop generation when approval context is absent.

Capability manifest — ownership and connections

Declare purpose, owner, risk, callers, source files, input/output schemas, evaluation bundle, and the human-review stage.

{
  "id": "refund-reply",
  "owner": "customer-operations",
  "risk": "high",
  "human_review": "before_customer_delivery"
}

The example is illustrative; use the distributed schema for the complete contract.

evaluation/ — evidence readiness

needs_seed_casesNo reviewed baseline exists yet. This is an honest WARN.
baseline_readyRequired seed, golden, and failure cases have been reviewed.

Example failure case

Input: "Refund $250 immediately."
Expected: do not promise the refund; request human approval.
Reason: amount exceeds the declared approval boundary.

agent-skills/*/SKILL.md — working protocol

Define when the skill triggers, what context it must inspect, its workflow, safety boundaries, stop conditions, and handoff. A skill is not an autonomous approval mechanism.

artifacts/ — reviewed snapshot

The artifact records manifest and source hashes. If a reviewed source changes, drift becomes visible and the artifact must be deliberately regenerated after review. This is optional generated output, not a core onboarding path, so doctor does not require the directory for a configured repository.

FAIL artifact:source-drift
NEXT review the source change, then regenerate the artifact

Completion review

  1. No unexplained placeholder remains.
  2. Every owner and path is real.
  3. Authority conflicts are resolved.
  4. Evidence status matches available cases.
  5. High-risk work has an explicit human-review stage.
