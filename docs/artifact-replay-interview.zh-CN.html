01 · 第一次停止

第一次回放根本没有走到构建。

我允许了一次不重试的真实回放，用它验证实际清理路径。结果 dry worker 先停了：这个环境有意不提供 PATH，但 manifest 检查仍然尝试启动裸 git。

这个失败反而证明限制真的生效了。最省事的做法是把 Git 塞回 worker，让报错消失；但那等于为了通过测试，削弱我原本想验证的边界。

决定：我没有重试已经耗尽的任务，也没有把扩大环境当成默认修复。

02 · 我做出的选择

我选择移动可信事实，而不是扩大 worker。

先用人话说：Git 可以留在外面。受限路径真正需要的，只是 controller 已经检查过的精确文件列表和身份摘要。落实到内部设计，就是把基于 Git 的入口检查与仅依赖文件系统的即时复核拆开。

03 · 第二个隐藏依赖

第一次修复是必要的，但静态检查证明它还不够。

把准入移到 controller 后，我沿 actual 路径继续检查。Caller 已经能到达 driver，但 driver 仍在导入同一个 Git checker。Dry worker 的问题修掉了，同样的耦合却还藏在更深一层。

底层修复大多由 Agent 提出，我对照想要保留的边界评估并批准：worker 继续没有 PATH，cleanup 仍然必须等证据验证完成。

面试追问

可能被问到的问题

为什么不恢复 PATH 或给 worker 提供 Git？

那是在用扩大执行边界解决数据流问题。Controller 已负责 Git 观测，而 driver 负责证明执行前的即时文件系统一致性。

为什么要多次观测 manifest？

它们回答不同问题：执行前的 Git 准入，以及资源分配前的文件系统一致性。

为什么失败时保留临时根目录？

在持久证据之前删除会破坏诊断现场，并产生没有依据的清理声明。Recovery 需要单独批准。

下一步会开发什么？

尚未决定。产品复核候选包括更清晰的清理后证据模板，或单独开展一次可移植性与重复性研究。
