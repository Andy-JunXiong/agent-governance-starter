# AgentGov 0.2.0rc1 release candidate

Status: candidate source is on `main`; not tagged, published, or deployed.

## Purpose

This candidate packages the first consumer-CI and governance-visibility slice
for review before a stable 0.2.0 release. It does not grant AgentGov permission
to create pull requests, merge changes, publish releases, or deploy adopting
projects.

## Added

- `agentgov status` text, JSON, and portable Markdown views showing adoption,
  CI integration, declared capability usage, governance surfaces, findings,
  the next action, and authority boundaries.
- `agentgov integrate github-actions` create-missing-only integration with a
  pinned wheel URL and SHA-256 digest, read-only permissions, report artifacts,
  and exact interactive confirmation.
- Version-aware managed workflows: stable 0.1 content remains byte-exact, while
  0.2-or-newer workflows add the Markdown status card and consumer upgrade
  review to the GitHub job summary and report artifact.
- `agentgov plan upgrade-pr`, a read-only current/candidate/blocked plan for one
  exact managed-workflow update. It creates no branch or pull request.
- `agentgov benefits compare`, a two-snapshot comparison with explicit finding
  denominators and no causal, prevented-incident, coverage, time-saving, or ROI
  claim.
- `agentgov review release`, a create-new-only bundle that automatically
  exercises the exact candidate wheel, source tests, consumer repository,
  status UI, and upgrade policy while leaving the human decision pending.
- `agentgov review upgrade`, a consumer-local bundle containing the stable
  upgrade plan, exact workflow patch, current project status, gates, and a
  pending project-owner decision without applying the change.

## Hardened

- Exact managed-workflow recognition now works across pinned AgentGov versions,
  allowing a reviewed managed workflow to remain eligible for later upgrades.
- Benefit comparison recalculates report summaries from findings and rejects
  altered or internally inconsistent counts.
- Release-manifest generation verifies that the requested channel, version,
  and wheel filename agree.
- Generated 0.2 manifests correctly declare compatibility from stable 0.1.0,
  rather than the pre-release 0.1.0.dev0 identifier.

## Compatibility

- Supported source tool version: `0.1.0`.
- Readable and target repository layout: `1.0`.
- Repository migrations: none.
- NYC may continue using its reviewed stable 0.1.0 workflow unchanged.
- The upgrade planner intentionally rejects this release-candidate channel;
  automated consumer proposals remain limited to validated stable releases.

## Known gates before stable 0.2.0

- Complete human review of this candidate and its release evidence.
- Approve the RC tag and GitHub Pre-release as a separate action. The dedicated
  RC workflow validates the tag against the package version, reruns the complete
  test suite, builds the wheel, validates the immutable release-candidate
  manifest, and publishes only after an approved RC tag is pushed.
- Approve stable-version source changes, commit, tag, push, and GitHub Release
  as separate actions after RC observation.
- Upgrade NYC only from a published, digest-verified stable manifest.
- Observe the first real NYC GitHub Actions run before claiming that the new
  status card or benefit evidence is active online.
- Keep the authenticated upgrade pull-request writer disabled until separately
  authorized and the reporting-only pilot has been evaluated.

The target release-notes URL in the local manifest is not live until a
corresponding human-approved GitHub release exists.
