30 秒定位

AI Coding Agent 可以写出测试通过的代码，同时又做了人根本没有要求的事。测试通过也不会告诉你，是不是已经有人同意让这个改动继续往前走。

我做 AgentGov，是为了把任务、这个任务允许修改的文件、当前运行产生的证据，以及人的决定连在仓库里。软件检查它能检查的事实，下一步仍然由人决定。

后来更难的问题是，我发现自己逐渐把更多工作放到 GitHub 和交付上，反而离 AgentGov 最初要解决的问题越来越远。

停顿点 1：如果对方只问“你做了什么”，讲到这里即可。

完整的两分钟回答

  1. 0:00–0:30 · 问题。Coding Agent 可以写出好代码，但仍然做了人没有要求的事。只看测试通过，不能知道它是否留在任务内、结果是否仍然对应当前代码，或者是否已经有人批准下一步。
  2. 0:30–0:55 · 我先做了什么。我从软件能够稳定检查的部分开始，做了一个小型 Python CLI。它读取任务、允许修改的文件和工作过程产生的证据，然后说明某件事通过、失败，还是仍然需要人判断。它不会把这些检查变成“这个改动是正确的”。
  3. 0:55–1:25 · 偏移如何发生。一次 consumer 实验暴露了安装、Windows 路径和 onboarding 摩擦，所以我先改这些，然后是 CI，再然后是 PR 流程。这些功能确实有用，测试也一直通过。但在连续几次常规价值复核中，我发现自己可以很清楚地解释 GitHub 机制，却越来越难把它们和原始业务问题连起来。我把累积实现和最初需求放在一起检查，确认产品方向已经偏移。
  4. 1:25–2:00 · 我改了什么，学到了什么。我保留了 PR 和 CI，但把它们移出中心。主产品回到开发循环：人定义任务，Agent 在约定边界里工作，当前文件和测试被检查，最后人决定下一步。验证能证明一个功能能工作，却不能告诉我是否还在做正确的产品。我现在自己做这项产品复核，而不是再把它自动化成一个新功能。

停顿点 2：这是完整默认回答。没有追问时，不必打开浏览器。

五到七分钟屏幕演示

  1. 0:00–3:00 · 运行场景。打开退款引导 Demo，从精确准入推进到 REVIEW_READY。
  2. 3:00–3:40 · 说明分工。直接使用 Demo 中的四个角色：人、模拟 Agent、AgentGov 和 Demo 脚本。
  3. 3:40–4:30 · 产品追问。只有对方追问产品为什么这样设计，才打开项目背景。
  4. 4:30–6:00 · 工程追问。工程岗位再打开artifact replay 深入案例。
  5. 6:00–6:30 · 按需核验。只有对方质疑某项结论时，才打开证据作品集。
  6. 6:30–7:00 · 诚实收尾。主动说明版本边界和一个相关未知项。

停顿点 3：引导式 Demo 之后，产品回答已经完整。停顿点 4：artifact replay 之后，工程回答已经完整。

只选一个岗位分支

软件或 AI 工程强调 fail-closed 边界、新鲜证据、确定性与建议性的区别，以及两次 replay 失败。底层修复大多由 Agent 提出，我负责审查批准。
平台或基础设施强调仓库原生契约、Host Adapter、CI 重放、权限分离、create-only 持久化，以及恢复不能静默替换 owner。
产品或技术产品强调持续价值复核、确认偏移、先回到核心 MVP，以及任务级验证为什么不能替代跨功能产品判断。

一眼看懂架构

Core 契约可移植的任务、finding、evidence 与 authority 语义。
仓库 Policy风险、路由、架构上下文和已准入范围。
Host Adapter原生交互和精确的人类决定协调。
产品界面CLI、Monitor、报告与公开证据页面。

人的权限保持独立：需求、产品与架构判断、例外、Git、发布、release 和部署。

准确说明“谁做了决定”

  • Airbnb：写入前准入、保留最初的人类准入，是我提出的；分阶段权限共同形成；独立 completion marker 由 Agent 提议、我批准。
  • Artifact replay：固定 Harness 边界共同形成；transport、manifest、readiness 和 filesystem 等底层修复大多由 Agent 提议、我批准；把清理前与清理后证据分开，是我坚持的决定。
  • 观察到系统运行不等于作者身份：一次有界运行不能证明广泛采用、可移植性、重复可靠性或独立保证。

常见面试追问

为什么不只是一个 linter？

因为它还把人的任务、架构上下文、路径范围、证据新鲜度、建议性复核和权限边界绑定起来，同时拒绝从静态检查推断需求价值。

为什么区分 PASS、WARN、FAIL 和 ADVISORY？

单一分数会掩盖契约满足、诚实的不完整、确定性失败，以及只能由人判断的问题之间的差别。

为什么不能自动检测产品漂移？

任务证据只能说明实现是否匹配已准入任务，不能说明一串各自合理的任务是否仍在推进正确的产品。跨功能的价值复核才提供这个判断。

最强的工程证据是什么？

简短产品回答用退款边界；工程深挖用 artifact replay：受限 worker 因隐藏 Git 依赖失败两次，限制没有放宽，可信事实移入边界内，唯一一次修复后回放无重试完成。

Artifact replay 的修复是谁设计的？

固定 Harness 边界共同形成。底层修复大多由 Agent 提出，我审查并批准；我坚持把清理前和清理后证据分开。

下一步做什么？

本指南不决定也不授权下一项需求。完成功能后应回到人的产品复核，而不是自动继续开发。

技术追问与诚实限制

  • 静态检查不能证明需求价值、架构质量、审阅者理解或测试充分性。
  • 稳定版 0.2.1 不包含最新开发源生命周期。
  • Replay 链保留不可变 reservation、create-only claim 和 immutable recovery；恢复不创建 replacement owner，也不授权 replay。
  • 一次 Airbnb 工作流和一次 artifact replay 不能证明广泛采用、可移植性、重复可靠性或生产安全。
